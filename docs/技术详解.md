# CoursePilot 技术详解（全栈）

本文把项目的**技术栈、架构分层、每条链路的实现细节、选型理由**完整讲一遍。所有参数与数字都来自当前代码与实测（2026-10-08）。

---

## 0. 一分钟读懂

**它是什么**：一个课程资料的 RAG 问答系统。上传 PDF / Markdown / TXT 或抓取官方文档网址后，系统自动解析、切分、向量化建索引；提问时先检索相关资料片段，再让大模型**只依据这些片段**作答，并逐条标注引用；检索不到依据时直接拒答。

**当前规模**：3 门课、14 篇文档、**556 个切片**（AI 应用开发 38 / 机器学习 208 / 课程资料 310）。

**一次问答的链路**：

```text
POST /api/chat
  → analyze   问题清洗
  → rewrite   双语查询改写（原问题 + 英文关键词）
  → retrieve  向量化 → 课程内召回 20 条 → 打分 → 重排取 6 条
  → grade     最高分 ≥ 0.45 → 生成；否则拒答
  → generate  拼装带页码的编号上下文 → qwen-plus 作答
  → 返回 答案 + 引用列表 + 工作流轨迹
```

**核心指标**（27 条标注用例）：AI 语料 Recall@5 **94.4%**、机器学习语料 Recall@5 **100%**、拒答判定准确率 **100%**。

## 1. 技术栈总览

| 层 | 技术 | 用在哪 | 为什么选它 | 放弃的备选 |
| --- | --- | --- | --- | --- |
| 语言 | Python 3.11+ | 全部后端 | LLM / 向量库 / PDF 解析生态最成熟 | Node.js（向量与 PDF 生态弱）、Java（迭代慢） |
| Web 框架 | FastAPI | API + 托管前端 | 自带 OpenAPI 与 Pydantic 校验，单进程即可演示 | Flask（无自动文档/校验）、Django（太重） |
| 数据校验 | Pydantic v2 | 请求/响应模型 | 与 FastAPI 原生集成，接口契约清晰 | 手写校验 |
| Agent 编排 | LangGraph | 五节点工作流 | 状态图可测试、可观测，条件边表达分支 | LangChain RetrievalQA（黑盒）、一堆 if/else |
| 向量化 | 百炼 `text-embedding-v3` | 切片与查询向量化 | 国内直连、中文好、OpenAI 兼容、按量计费 | `bge-m3`（需另建服务）、本地哈希（仅离线兜底） |
| 生成 | 百炼 `qwen-plus` | 基于上下文作答 | 中文表达强、上下文长、便宜 | DeepSeek（换三行配置）、本地小模型 |
| 重排 | 硅基流动 `BAAI/bge-reranker-v2-m3` | 20 条候选精排取 6 | 交叉编码器精度高、有免费额度、无需本地 GPU | 百炼 `gte-rerank-v2`（免费额度用尽）、本地 cross-encoder（CPU 慢） |
| 向量库 | 本地 JSON（可切 Qdrant） | 向量存储与相似度检索 | 演示零依赖；接口抽象后切 Qdrant 不改业务代码 | FAISS（需自管持久化与过滤）、Milvus（运维重） |
| 关系库 | SQLite（可切 PostgreSQL） | 课程/文档/切片/会话 | SQLAlchemy 统一模型，演示零依赖、部署可切 | 只用文件（无事务与查询能力） |
| ORM | SQLAlchemy 2.x | 数据建模 | 同一套模型适配 SQLite 与 PostgreSQL | 裸 SQL（迁移成本高） |
| 解析 | pypdf + BeautifulSoup | PDF 抽取 / 网页正文 | 纯 Python，无需外部服务 | pdfplumber（更慢）、无头浏览器（重） |
| HTTP | httpx | 调用外部模型接口 | 超时可控、易于封装重试 | requests（异步支持弱） |
| 前端 | 原生 HTML/CSS/JS | 页面与交互 | 无构建链，`start.cmd` 一跑就能用 | React/Vue（构建链与依赖无收益） |
| 测试 | pytest | 12 条后端测试 | FastAPI 生态、上手快 | unittest（繁琐） |
| 部署 | 一键脚本；Docker Compose（配置级） | 启停 / 可选容器化 | 演示场景本地脚本最稳 | Compose 未实跑（本机无 Docker） |

## 2. 系统架构

### 2.1 进程模型

**单进程**：一个 uvicorn 进程同时提供 `/api/*` 接口和前端静态文件（`StaticFiles` 挂在 `/`）。好处是部署与演示只需一条命令；代价是不能水平扩展（当前场景不需要）。

### 2.2 启动流程

```text
uvicorn 启动
  → FastAPI lifespan
      → init_db()         建表（SQLAlchemy create_all）
      → seed_demo_data()  库里没有课程时，播种示例课程与 14 节讲义并建索引
  → 开始接收请求
```

### 2.3 代码地图

| 路径 | 职责 |
| --- | --- |
| `backend/app/main.py` | 组装 FastAPI、CORS、生命周期、挂载前端静态文件 |
| `backend/app/config.py` | 从 `.env` 读取全部配置（`lru_cache`，**改配置必须重启**） |
| `backend/app/database.py` | 引擎、会话工厂、健康检查、建表 |
| `backend/app/models.py` | 7 张表：课程、文档、切片、网页来源、导入任务、会话、消息 |
| `backend/app/schemas.py` | 全部请求/响应模型（含评测与对话轨迹） |
| `backend/app/routers/*.py` | 6 组接口：courses / documents / imports / chat / evaluations / system |
| `backend/app/services/parsing.py` | PDF/MD/TXT 抽取与**切分** |

| `scripts/run_evaluation.py` | 评测命令行（`--suite` / `--top-k` / `--offline` / `--refusal`） |

## 3. 数据层

### 3.1 关系模型（SQLAlchemy 2.x）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `courses` | id / name / description / color | 课程 |
| `documents` | id / course_id / original_name / stored_path / mime_type / **status** / error_message / chunk_count | 文档与解析状态 |
| `chunks` | id / document_id / course_id / chunk_index / page_number / section / content / vector_id | 切片元数据（正文同时存进向量库 payload） |
| `document_sources` / `import_jobs` | 来源网址、抓取任务状态 | 网页导入溯源 |
| `conversations` / `messages` | 会话与消息（含引用与轨迹 JSON） | 支持历史回看 |

**文档状态机**：`queued → processing → ready`，失败落 `failed` 并把错误写进 `error_message`——出问题能定位到具体文档和原因，而不是只有一个笼统的"失败"。

### 3.2 为什么 ORM + 可切换数据库

SQLite 让演示零依赖（数据库文件随项目走），PostgreSQL 用于部署；两者通过 SQLAlchemy 同一套模型打通，切换只改连接串。这是**用一层抽象换掉一类环境问题**。

### 3.3 向量存储抽象

```python
class LocalVectorStore:   # 本地 JSON 文件
    def upsert(course_id, points) ...
    def search(course_id, vector, limit, query) ...
    def delete_by_document(course_id, document_id) ...

class QdrantVectorStore:  # 远端 Qdrant，同样的方法签名
    ...
```

业务代码只依赖方法签名，`VECTOR_BACKEND` 决定用哪个实现。**注意**：两者打分口径不同（本地是 `0.8×余弦 + 0.2×关键词`，Qdrant 是纯余弦），切换后必须重新标定拒答阈值——这一点同时写进了文档与代码注释。

## 4. 文档接入与切分

### 4.1 两条入口

| 入口 | 流程 |
| --- | --- |
| 上传文件 | `POST /api/courses/{id}/documents` → 落盘 → 后台任务 → 解析/切分/向量化 → 状态置 ready |
| 网址导入 | `POST /api/courses/{id}/imports/web` → 建 ImportJob → 后台抓取（可限定同路径、限制页数）→ 提取正文 → 走同一条索引流水线 |

### 4.2 切分三步

```text
① 页级抽取：pypdf 逐页读取并保留页码（切片不跨页，引用可定位到页）
② 去噪：跨页重复行（出现率 ≥40% 且 ≥3 页）判为页眉/目录条丢弃；
        不足 12 字、不含字母汉字、纯符号的块丢弃
③ 窗口切分：700 字、重叠 100 字；边界优先级
   标题 → 段落空行 → 句子结尾（。！？；!?; 与英文句点+空格）→ 空格 → 硬切
   重叠区向后对齐到最近句首，避免半句话重复
```

**真实追踪**：`03机器学习-逻辑回归.pdf` 26 页 → **26 个切片**（每页 20~300 字，一页一片，700 上限未触发）；`FastAPI ¶.md` 单页 14,236 字 → **26 个切片**（24 片落在句子边界）。详见《切分策略详解》。

## 5. 向量化（含缓存与重试）

| 项目 | 值 |
| --- | --- |
| 模型 | `text-embedding-v3`（OpenAI 兼容接口） |
| 维度 | 1024 |
| 单批上限 | **10 条**（供应商硬限制，超出直接 400） |
| 超时 / 重试 | 30 秒 / 3 次指数退避（对 429、5xx 与网络异常重试） |
| 缓存 | 落盘 JSON，key = `sha256(model + text)`，默认上限 2000 条，命中则零调用 |
| 兜底 | 无可用 Key 时降级为本地哈希向量（无语义能力，仅保证系统能跑） |

**为什么要缓存**：同一模型同一文本的向量是确定的，缓存让重复提问与重建索引都变快，同时把"接口抖动"这条长尾压掉——实测缓存命中时单次检索 **110~150 毫秒**。

## 6. 检索链路

### 6.1 五个步骤

```text
① 查询改写  原问题 + LLM 生成的英文关键词（代码强制拼接，防止模型整句翻译丢掉中文）
② 向量化    text-embedding-v3 → 1024 维（命中缓存则零调用）
③ 候选召回  限定课程范围，取 RETRIEVAL_CANDIDATES=20 条
④ 打分排序  本地：0.8 × 余弦相似度 + 0.2 × 关键词覆盖率（截断到 [0,1]）
            可选：BM25 稀疏检索 + RRF 融合（默认关闭，实测负收益）
⑤ 重排      bge-reranker-v2-m3 对 20 条精排，取 RETRIEVAL_TOP_K=6 条
```

### 6.2 为什么需要重排

向量检索是"双塔"结构：问题和切片分别编码后比距离，无法做词级交互。交叉编码器把「问题 + 切片」成对送进模型，能捕捉细粒度相关性——**它解决的是排序问题**（正确答案已在候选集、但排在 6~10 位），而不是召回问题。

### 6.3 拒答阈值怎么定

| 问题类型 | Top1 分数区间 |
| --- | --- |
| 相关问题（9 条） | 0.527 ~ 0.747 |
| 无关问题（5 条） | 0.224 ~ 0.413 |

中间存在干净分界带 → 阈值定 **0.45**；哈希兜底模式自动降到 0.05，避免切换后端后全部拒答。

### 6.4 延迟构成

| 环节 | 典型耗时 |
| --- | --- |
| 查询改写（LLM） | 约 1 秒 |
| 查询向量化 | 约 0.7 秒（缓存命中约 0） |
| 本地向量检索（556 片） | 几十毫秒 |
| 重排（20 条） | 约 0.3~1 秒 |
| **合计（在线完整链路）** | **约 2~3 秒** |

结论：延迟几乎全在外部调用上，优化方向是缓存与并发，而不是改检索算法。

## 7. Agent 工作流（LangGraph）

### 7.1 概念对应

| LangGraph 概念 | 本项目中的体现 |
| --- | --- |
| `StateGraph` | 整条问答流程 |
| `Node` | analyze / rewrite / retrieve / grade / generate / refuse |
| `State` | 问题、检索查询、命中切片、决策、答案、轨迹 |
| `Conditional Edge` | grade 输出 `generate` 或 `refuse`，据此路由 |
| `END` | 生成或拒答结束流程 |

### 7.2 为什么用状态图而不是 if/else

1. **每个节点可单独测试与替换**：改写策略、检索实现、判定阈值都能独立改动。
2. **拒绝是一等公民**：把"资料不足"显式建模成一条分支，而不是藏在提示词里指望模型自觉。
3. **可观测**：轨迹（经过哪些节点、检索多少条、决策结果、耗时）随答案返回，前端可视化"系统怎么得出结论"。
4. **可降级**：未安装 LangGraph 时自动退化为顺序执行同一批节点，功能不受影响。

## 8. 生成环节

### 8.1 上下文组装

命中的 6 条切片按下面的结构拼成上下文，再交给模型：

```text
[1] {文档名}
页码: {page_number}
{切片正文}

[2] ...
```

配合系统提示词约束：**只依据给定上下文作答、用 `[1][2]` 标注引用、资料不足就明确说明、跟随提问语言**。温度设为 0.1，减少随机发挥。

### 8.2 为什么这样设计

- **编号 + 文档名 + 页码**：让引用可点击回溯，也迫使模型把结论绑定到具体来源。
- **低温度**：问答场景要的是稳定复现，不是创意。
- **未命中就拒答**：判断发生在生成之前（grade 节点），而不是让模型自己决定要不要编。

## 9. 评测体系

### 9.1 用例结构

```json
{
  "question": "Qdrant 和 PostgreSQL 在 RAG 系统里分别负责什么？",
  "expected_terms": ["Qdrant", "PostgreSQL"],
  "relevant": [
    {"document": "RAG 与 Agent 课程讲义.md", "chunk_index": 3},
    {"document": "RAG 与 Agent 课程讲义.md", "chunk_index": 4}
  ],
  "answerable": true
}
```

| 字段 | 作用 |
| --- | --- |
| `question` | 测试问题 |
| `expected_terms` | 期望出现在命中切片里的关键词（一致性检查用） |
| `relevant` | **标注的标准答案切片**（Recall / Precision / NDCG 的依据） |
| `answerable` | `false` 表示资料里没有答案，系统应当拒答 |

当前：**27 条用例**（22 条可回答 + 5 条应拒答），覆盖 2 门课程、246 个切片。

### 9.2 八个指标

| 指标 | 定义 | 回答什么问题 |
| --- | --- | --- |
| Recall@k | 召回的相关切片 / 标注切片总数 | 该找的资料有没有找全 |
| Precision@k | 召回的相关切片 / 返回条数 | 返回里有多少是相关的 |
| NDCG@k | 带位置折扣的排序质量 | 相关内容排得够不够靠前 |
| MRR | 平均 `1 / 首个相关切片排名` | 第一个正确答案出现得早不早 |
| Hit Rate | top_k 里至少命中一条的用例比例 | 最宽松的"有没有找到" |
| 关键词覆盖率 | 期望词在最佳命中切片里的占比 | 答案要素齐不齐 |
| 判定准确率 | （可答走生成 + 应拒答走拒答）/ 总用例 | 判断边界是否可靠 |
| 检索延迟 | 向量化 + 检索耗时（不含生成） | 检索侧性能 |

**为什么要这么多**：只有 Hit Rate 和 MRR 时分不清「召回不到」和「排序不好」，而这两类问题的解法完全不同——前者靠查询改写与切分，后者靠重排。Recall 与 NDCG 的差值就是判断依据。

### 9.3 防自欺的两个机制

1. **标注校验**：跑之前先核对标注切片是否存在、期望词是否真的落在标注切片里——防止写出不存在的切片。
2. **遗漏标注提示**：列出「同样包含全部期望词但未被标注」的切片，交人工复核。这条检查抓到过一次真实错误（标准答案标窄，导致 Recall 虚低）。

### 9.4 消融实验与离线模式

- **消融**：一次只改一个环节，比较改动前后的指标——BM25 就是这样被判定为负收益并关闭的。
- **离线模式**：`python scripts\run_evaluation.py --offline` 跳过改写与重排、查询向量直接命中缓存，**两个套件 8.2 秒跑完、零外部请求**，用于断网或无额度时验证流程与标注。

### 9.5 当前实测结果

| 指标 | AI 应用开发（38 切片） | 机器学习（208 切片） |
| --- | --- | --- |
| Recall@3 | 77.8% | 73.1% |
| **Recall@5** | **94.4%** | **100%** |
| Precision@5 | 26.7% | 29.2% |
| NDCG@5 | 0.911 | 0.838 |
| MRR | 0.917 | 0.791 |
| Hit Rate@5 | 100% | 100% |
| 判定准确率 | 100% | 100% |
| 平均检索延迟 | 2.19 s | 3.19 s |

（对比：仅向量召回时 AI 语料 Recall@5 为 72.2%、机器学习 96.2%——查询改写与重排分别贡献了这两处的提升。）

## 10. 配置体系（.env 全参数）

| 参数 | 当前值 | 作用与调整后果 |
| --- | --- | --- |
| `LLM_PROVIDER` / `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` | openai / 百炼兼容地址 / 已配置 / `qwen-plus` | 生成与查询改写；换 DeepSeek 只需改这三项 |
| `EMBEDDING_PROVIDER` / `EMBEDDING_MODEL` / `EMBEDDING_DIM` | qwen / `text-embedding-v3` / 1024 | **换模型或改维度必须重建索引**，否则向量空间不一致 |
| `EMBEDDING_BATCH_SIZE` | 10 | 供应商单批上限，改大直接 400 |
| `EMBEDDING_CACHE_ENABLED` / `EMBEDDING_MAX_RETRIES` / `EMBEDDING_TIMEOUT_SECONDS` | true / 3 / 30 | 缓存与重试策略，直接影响长尾延迟 |
| `VECTOR_BACKEND` | local | `local`（JSON）或 `qdrant`；切换后**必须重标阈值** |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | 700 / 100 | 切分参数，改动后需重建索引 |
| `RETRIEVAL_CANDIDATES` | 20 | 进入重排的候选数；调大召回更全但重排更慢更贵 |
| `RETRIEVAL_TOP_K` | 6 | 最终交给模型的切片数；调大上下文更全但更贵、噪声更多 |
| `HYBRID_RETRIEVAL_ENABLED` | false | BM25 + RRF 融合开关（实测负收益，默认关） |
| `QUERY_REWRITE_ENABLED` | true | 查询改写开关；关掉会丢掉跨语言召回的收益 |
| `RERANK_ENABLED` / `RERANK_PROVIDER` / `RERANK_MODEL` | true / siliconflow / `BAAI/bge-reranker-v2-m3` | 重排配置；切供应商只需改前两项 |
| `RERANK_API_KEY` | 已配置 | 为空时自动复用 `LLM_API_KEY` |
| `MIN_RETRIEVAL_SCORE` | 0.45 | 拒答阈值；调高更保守（更易拒答），调低更激进 |
| `MAX_UPLOAD_MB` / `CORS_ORIGINS` | 25 / 本机地址 | 上传限制与跨域白名单 |

## 12. 性能与鲁棒性

### 12.1 三条性能结论

1. **延迟几乎全在外部调用**：检索本地部分只有几十毫秒，1 秒花在改写、0.7 秒花在向量化、0.3~1 秒花在重排。
2. **缓存是性价比最高的优化**：命中缓存时单次检索从 ~2 秒降到 110~150 毫秒。
3. **平均值会骗人**：曾出现单次 20 秒的检索（供应商抖动），平均值被拉高到 2.5 秒；要盯长尾，所以加了重试与超时上限。

### 12.2 四条降级路径

| 情况 | 行为 | 是否可见 |
| --- | --- | --- |
| embedding 抖动 | 30 秒超时 + 3 次指数退避重试 + 缓存兜底 | 日志 |
| 查询改写失败 | 回退用原始问题检索 | 流程不中断 |
| 重排失败 / 无额度 | 保留检索顺序（fail-open） | 日志 + `/api/system/health` 的 `last_error` + 轨迹里的 `reranked=false` |
| 断网 / 无任何额度 | 离线评测与哈希向量兜底 | 评测数字会明显下降，报告里必须写明模式 |

**设计原则**：每一环都可以单独失效，但整条链路不能断；同时降级必须可见——否则就是自欺欺人。

## 13. 选型问答（为什么不用 X）

| 问题 | 回答 |
| --- | --- |
| 为什么不用 Flask / Django？ | Flask 没有自动接口文档与数据校验，Django 的 ORM/Admin 对本项目是负担；FastAPI 一个进程就能同时提供 API、文档与静态页面 |
| 为什么不用 LangChain 的 RetrievalQA？ | 它是黑盒：拿不到节点级轨迹，也不方便在检索与生成之间插自定义判断；LangGraph 把流程显式建模成状态图，拒绝分支与轨迹都是白盒 |
| 为什么向量库先用本地 JSON？ | 556 个切片的规模下，线性扫描只要几十毫秒，零依赖能让对方一条命令跑起来；接口已抽象，量级上来切 Qdrant 不用改业务代码 |
| 为什么不用 FAISS / Milvus？ | FAISS 需要自己管持久化与元数据过滤，Milvus 运维成本高；本项目需要的是"能切换、够用"，而不是"最大吞吐" |
| 为什么用 SQLite 还要配 PostgreSQL？ | 演示用 SQLite 零依赖，部署用 PostgreSQL；SQLAlchemy 让两者共用一套模型，切换只改连接串 |
| 前端为什么不用 React？ | 交付对象是面试官与老师：`start.cmd` + 原生页面比"装 Node、装依赖、构建"更可靠；界面复杂度也没到需要框架的程度 |
| 为什么向量化用百炼而不是 BGE？ | 一是依赖最少（改写、向量化、生成共用一个 Key 与计费）；二是中文语料实测够用；三是切换成本低——`EMBEDDING_PROVIDER` 支持 `bge`，README 有 SiliconFlow 与 Ollama 两套模板。**但我没有做过 bge-m3 的 A/B，所以只能说"够用+省事"，不能说"更好"** |
| 重排为什么最后选了 bge-reranker-v2-m3？ | 百炼 `gte-rerank-v2` 免费额度用尽，而硅基流动的 bge-reranker 有免费额度、判别力强（正确 0.943 / 无关 0.016）、且不需要本地 GPU；本地 cross-encoder 在无 GPU 的机器上会带来数秒延迟 |
| 为什么评测自己写而不用 RAGAS？ | 需求是"检索侧可复现 + 可离线 + 指标透明"，自建约 300 行就够；RAGAS 更重，且生成侧指标需要额外模型调用 |
| BM25 为什么实现了却默认关？ | 实测在这份课件语料上是负收益（机器学习 Recall@5 96.2% → 88.5%）：术语重复度高，关键词信号把近似切片推上来挤掉正确答案。保留开关与代码，用数据说明为什么关 |

## 14. 已知局限与下一步

### 局限（都写进文档，不藏着）

1. 语料规模仍偏小（556 切片、27 条用例），指标只能看趋势，不能当行业结论。
2. 评测只覆盖检索侧；生成侧的忠实度、引用正确性尚未量化，目前靠人工抽查。
3. 标准答案由人工标注，重复内容的判断有主观空间，脚本只能提示不能替代人。
4. 只支持单轮问答，没有多轮指代消解。
5. Docker Compose 与 Qdrant/PostgreSQL 只写了配置，本机没有 Docker，**未实跑验证**。
6. 依赖外部模型服务：额度、网络波动会直接影响效果与延迟（已有降级与可见性措施）。

### 下一步优先级

| 优先级 | 事项 | 为什么 |
| --- | --- | --- |
| 高 | 生成侧评测（LLM-as-judge 打忠实度与引用正确性） | 检索已经能量化，生成侧还是空白 |
| 高 | 多轮记忆与指代消解 | 追问不需要重复上下文，是真实使用场景的刚需 |
| 中 | 工具调用（Function Calling） | 让 Agent 能查结构化数据或访问外部服务 |
| 中 | 换更强 embedding 做 A/B（如 bge-m3） | 跨语言检索还有约 5.6% 的空间 |
| 低 | Qdrant / PostgreSQL 实跑与压测 | 数据量到万级切片后再做，避免过早优化 |
