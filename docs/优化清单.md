# CoursePilot 优化清单

**做了什么 · 为什么做 · 数据验证**

本文按「效果 / 数据 / 鲁棒性 / 可度量性」四类整理项目里的全部优化。每一条都对应一个被评测量化的短板，而不是因为某个技术看起来更先进。

---

## 一、效果类（直接影响回答质量）

| 提升 | 为什么做 | 数据 |
| --- | --- | --- |
| **新增查询改写节点** | 中文问题直接匹配英文切片吃亏：问「哪两个交互式文档界面」，切片里写的是 `Swagger UI / ReDoc` | 英文语料 **Recall@5 72.2% → 88.9%**，MRR 达到 1.000 |
| **新增 rerank 精排** | 正确切片常落在第 6~10 位，向量相似度不足以做精细排序 | 机器学习语料 **Recall@5 96.2% → 100%**，NDCG@5 0.887 → 0.896 |
| **拒答阈值标定 0.12 → 0.45** | 阈值 0.12 时 5 条无关问题**全部**进入生成节点，判断节点形同虚设 | 判定准确率提升到 **100%**（相关问题最低 0.527、无关问题最高 0.413，中间存在干净分界带） |
| **示例讲义扩充 2 → 12 个切片** | 示例语料太薄，很多问题覆盖不到 | 英文语料 Recall@5 再提升到 **94.4%** |

## 二、数据侧（切分质量）

| 提升 | 为什么做 | 数据 |
| --- | --- | --- |
| **结构感知切分**：标题 → 段落 → 句子 → 空格；重叠区对齐到句首 | 旧实现会在词中间切断（出现过以 `lix (ref)`、`PI a ton` 开头的切片），页眉与目录行被当成正文 | 切片 243 → 236；含同一答案的重复切片 4 → 3；不再有从断词开始的切片 |
| **跨页重复行过滤** | 课件每页都印着相同的目录条，进了向量空间就是纯噪声 | 命中并丢弃（例如「3.逻辑回归求解」「机器学习-引言 2026年03月」） |
| **噪声块过滤** | 页码、装饰线、「谢 谢！」这类页面没有任何检索价值 | 去掉空白后不足 12 字、或不含字母汉字的块直接丢弃 |

## 三、鲁棒性（系统不中断）

| 提升 | 为什么做 | 数据 |
| --- | --- | --- |
| **向量缓存 + 3 次指数退避重试 + 超时降至 30 秒** | 供应商接口抖动会把单次检索拖到 20 秒以上，平均值掩盖长尾 | 长尾消失；缓存命中时单次检索 **110~150 毫秒** |
| **四条降级路径**：改写失败回退原文 / 重排失败保留顺序 / 缓存兜底 / 离线模式 | 任何一环失效都不能让整条链路中断 | 当前 rerank 额度用尽仍在正常服务，只是机器学习指标从 100% 落到 92.3% |
| **降级必须可见**：日志 + `health.rerank.last_error` + 修正 `reranked` 语义 | fail-open 会静默降级，等于自己骗自己 | 修掉了「调用失败也报 `reranked=true`」的假信号 |
| **离线评测模式** | 无额度或断网时无法验证改动的正确性 | 两个套件 **8.2 秒跑完、零外部请求** |

## 四、可度量性（能发现问题）

| 提升 | 为什么做 | 数据 |
| --- | --- | --- |
| **评测指标从 4 个扩到 8 个**（新增 Recall@k、Precision@k、NDCG@k、判定准确率） | 只有 Hit Rate 和 MRR 时，分不清「没召回」还是「排序差」 | 27 条标注用例（22 条可回答 + 5 条应拒答），覆盖 2 门课程 246 个切片 |
| **标注校验 + 遗漏标注提示** | 第一轮把标准答案标窄了，导致 Recall 虚低（假故障） | 脚本自动列出「同样包含期望词但未被标注」的切片，交人工复核 |
| **消融实验** | 防止「加了一堆技术，却不知道哪个真有用」 | 一次性对比：仅向量 / +BM25 / +rerank+改写 |

## 五、两个「不做」也是提升

1. **BM25 混合召回实现了但默认关闭**：实测在课件语料上是**负收益**（机器学习 Recall@5 96.2% → 88.5%），因为课件术语重复度高，关键词信号会把大量近似切片推上来，反而挤掉正确切片。代码保留、配置可开，但默认关闭，并用数据说明原因。
2. **没有为了好看堆技术**：没有硬上分布式向量库、没有宣称支撑百万级数据。**「用评测决定保留还是回退」本身，比多接一个组件更能说明工程能力。**

## 六、优化顺序（方法论）

```text
① 先建评测  → 27 条标注用例，指标覆盖召回与排序
② 分清病因  → 失败是「召回不到」还是「排序不好」
③ 对症下药  → 跨语言召回不到 → 查询改写
               排序不好       → rerank 精排
               粒度太脏       → 结构感知切分
④ 消融验证  → 一次只改一个环节，比较改动前后
⑤ 保留或回退 → 有收益就留，负收益就关（BM25 被否决）
⑥ 全程可降级 → 每一环都能单独失效，链路不能断
```

**面试可直接说的一句话：**

> 我的优化顺序是先用评测把失败分成「召回不到」和「排序不好」两类，再对症下药——跨语言召回不到就加查询改写，排序不好就加 rerank；每一环都配了降级路径，并用消融实验确认收益。期间 BM25 被数据否决，我就关掉它，而不是留在简历里。

## 七、下一步计划

| 方向 | 为什么值得做 |
| --- | --- |
| 多轮记忆与指代消解 | 现在只支持单轮，追问需要重复上下文 |
| 工具调用（Function Calling） | 让 Agent 能查结构化数据或访问外部服务，而不只依赖文档检索 |
| 生成侧忠实度评测（LLM-as-judge） | 当前只量化了检索，回答是否被证据支撑还没量化 |
| 换更强 embedding 做 A/B（如 bge-m3） | 跨语言检索还有 11% 的空间，值得用同一套评测对比后再决定 |
| 分级策略 | 简单问题走轻链路、复杂问题才启用改写与重排，控制成本与延迟 |
