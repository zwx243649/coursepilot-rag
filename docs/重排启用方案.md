# 重排（Rerank）状态与启用方案

## 一、当前状态

| 项目 | 状态 |
| --- | --- |
| 重排模型 | DashScope `gte-rerank-v2` |
| 接口返回 | **403 `AllocationQuota.FreeTierOnly` —— 免费额度已用尽** |
| 当前行为 | 每问仍会尝试调用重排，失败后自动保留检索顺序（fail-open），并在日志与 `/api/system/health` 的 `rerank.last_error` 中留痕 |
| 结论 | **这不是设计目标，只是临时状态**；目标是让重排真正生效 |

同日实测：`gte-rerank` 返回 `AccessDenied`，`qwen3-reranker-*` 与 `text-rerank` 均返回「模型不存在」——也就是说，在当前账号下这个供应商的重排已经无法继续使用。

## 二、重排值多少（同一套 27 条用例的消融数据）

| 指标 | 不重排 | 重排生效 | 差异 |
| --- | --- | --- | --- |
| 机器学习语料 Recall@5 | 92.3% | **100%** | +7.7 个百分点 |
| 机器学习语料 NDCG@5 | 0.843 | **0.896** | +0.053 |
| 英文语料 NDCG@5 | 0.792 | **0.986** | +0.194 |
| 英文语料 MRR | 0.759 | **1.000** | +0.241 |

结论：重排主要解决**排序问题**——把已经召回、但排在第六到第十位的正确切片提到前五。它救不了「根本没召回」的情况（那要靠查询改写）。

## 三、三条恢复路径

| 方案 | 成本 | 谁做什么 | 生效时间 | 风险 |
| --- | --- | --- | --- | --- |
| **A. 百炼开通付费 / 关闭「仅免费额度」** | 按量计费（重排单价很低） | 你：百炼控制台 → 关闭「仅使用免费额度」或充值 | 约 5 分钟 | 无 |
| **B. 换 SiliconFlow 的 `bge-reranker-v2-m3`** | 有免费额度，超出后按量 | 你：注册拿 Key；我：改 2 行配置 + 验证 | 约 10 分钟 | 低（代码已支持） |
| C. 本地部署 cross-encoder（如 `bge-reranker-base`） | 零 API 成本 | 下载约 1GB 模型 + 安装 torch；CPU 每次推理 1~3 秒 | 1~2 小时 | 较高（这台机器 9/17、9/18、9/27 三次蓝屏，跑重负载模型有风险） |

---

## 四、建议

- **最快**：方案 A——你的账号里 embedding 与生成都正常，说明账号可用，只是重排的免费额度单独用尽。
- **最省**：方案 B——SiliconFlow 有免费额度，而且**代码已经改造成可切换供应商**，切过去只需两行配置。
- **不建议**：方案 C——本地模型虽然不依赖任何 Key，但这台机器最近连续蓝屏，不适合跑重负载推理。

---

## 五、切换步骤（方案 B，拿到 Key 后由我执行）

1. 你：注册 SiliconFlow → 控制台创建 API Key（免费额度覆盖 `BAAI/bge-reranker-v2-m3`）
2. 我：修改 `.env` 两行：

```dotenv
RERANK_PROVIDER=siliconflow
RERANK_API_KEY=sk-你的硅基流动Key
```

（Base URL 与模型名会自动切到 `https://api.siliconflow.cn/v1/rerank` 与 `BAAI/bge-reranker-v2-m3`，不需要额外配置；两种接口的请求/响应格式差异已经在代码里适配好。）

3. 重启服务并验证：

```powershell
python scripts\run_evaluation.py --top-k 5
```

**验证判据（三条同时满足才算真的生效）**：

| 检查项 | 主路径生效 | 降级中 |
| --- | --- | --- |
| `/api/system/health` → `rerank.last_error` | `null` | `rerank request failed` |
| 回答 trace 里的 `reranked` | `true` | `false` |
| 评测：机器学习语料 Recall@5 | **100%** | 92.3% |

## 六、为什么代码里仍然保留降级路径

保留降级**不等于用降级糊弄**，两者的区别在于「是否可见」：

- 重排是**提质手段**，不是生存依赖。供应商挂掉时，系统应该继续给出可用答案，而不是整体报错。
- 但降级必须暴露出来：日志、`/api/system/health`、回答轨迹里的 `reranked` 字段，三处都能看出来当前跑在哪条路径。
- 最重要的一条纪律：**报告里的数字必须来自主路径生效的状态**。如果重排没生效，结论里就要写明并说明原因——就像本文第一节点明的那样。

## 七、代码侧已做的准备（本次完成）

| 改动 | 说明 |
| --- | --- |
| 重排支持多供应商 | `RERANK_PROVIDER` 支持 `dashscope` 与 `siliconflow`，两家的请求/响应格式差异已在 `rerank.py` 内适配 |
