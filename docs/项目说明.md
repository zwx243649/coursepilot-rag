# CoursePilot 项目说明

面向大学生实习作品集的课程资料 RAG 问答系统。本文按「模块划分 → 技术栈与选型 → 运行效果 → 评测体系」组织，可以直接用于汇报、答辩或者跟同学讲清楚这个项目。

## 1. 项目解决什么问题

老师给的课件、官方文档、PDF 讲义通常是几十上百页，直接丢给大模型提问有两个问题：模型可能没见过这些资料，以及模型会编造原文里不存在的内容。

CoursePilot 的做法是：用户上传资料（PDF / Markdown / TXT，或直接导入官方文档网址），系统解析、切片、向量化并建立索引；提问时先在索引里做语义检索，把命中的原文片段交给大模型，让它**只依据这些片段**生成回答，并逐条标注引用来源。如果检索不到足够相关的内容，工作流会走「拒绝」分支，明确说资料不足，而不是让模型自由发挥。

- 运行方式：FastAPI 单进程同时提供 API 和前端页面，访问 `http://127.0.0.1:8000`
- 启停命令：`.\start.cmd` / `.\stop.cmd`

## 3. 一次提问的完整链路

1. 前端 `POST /api/chat`，带上课程 ID 和问题；用户消息先落库。
2. `analyze` 节点清洗问题（去掉「请问」「帮我」这类前缀，得到检索用的查询词）。
3. `retrieve` 节点把问题向量化，在**该课程范围内**检索 top_k=6 个切片。
4. `grade` 节点拿 Top1 相似度分数和阈值比较，决定下一步走 `generate` 还是 `refuse`。
5. `generate` 节点把命中的片段拼成编号上下文，交给 qwen-plus，提示词要求：只依据给定上下文回答、用 `[1]` `[2]` 标注引用、资料不足就明说。
6. 返回答案 + 引用列表 + 工作流轨迹（经过哪些节点、决策结果、检索条数、耗时），前端把轨迹和引用一起渲染出来。

## 4. 技术栈与选型原因

| 技术 | 承担什么 | 为什么选它 | 放弃的备选 |
| --- | --- | --- | --- |
| FastAPI | API 服务 + 托管前端静态文件 | 自带 OpenAPI 文档和数据校验，异步够用，一个进程就能演示 | Flask（无自动文档/校验）、Django（太重，Admin/ORM 优势用不上） |
| Pydantic | 请求/响应模型与校验 | 与 FastAPI 原生配合，接口契约清晰 | 手工校验字典 |
| SQLAlchemy 2.x | 数据层 ORM | 同一套模型代码可在 SQLite 与 PostgreSQL 间切换，便于从演示平滑升级 | 直接写 SQL（迁移成本高） |
| 关系数据库 | 课程、文档、会话、消息 | 当前用 SQLite：零依赖、可随项目携带；部署路径已配 PostgreSQL | 只用文件存储（并发与事务能力不足） |
| 向量数据库 | 切片向量与相似度检索 | 代码抽象成统一接口，当前用本地 JSON 文件（28 切片规模足够、零依赖），切换到 Qdrant 只改 `.env` 与容器配置 | FAISS（需自己管理持久化与过滤）、Milvus（运维成本高） |
| Embedding：DashScope `text-embedding-v3` | 把切片和问题转成 1024 维向量 | 国内直连稳定、按量计费便宜、OpenAI 兼容接口、中文语料表现好；一个 Key 同时覆盖检索和生成 | `bge-m3`（SiliconFlow / Ollama，配置模板已写在 README）、本地哈希向量（仅离线兜底，无语义能力） |
| 生成：`qwen-plus` | 基于检索片段生成回答 | 中文表达强、上下文够长、价格低，兼容 OpenAI 协议 | DeepSeek（改 `LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY` 三行即可切换）、本地小模型（无 GPU 时延迟和效果都受影响，适合纯离线演示） |
| LangGraph | 把检索问答组织成状态图 | 每个节点可独立测试替换，条件边让「拒绝」成为一等公民，运行轨迹能回传前端展示；后续加重试、重排、多轮只需加节点 | 一坨 `if/else`（难扩展、无法输出轨迹）、LangChain `RetrievalQA`（黑盒，不好插自定义判断） |
| 原生 HTML/CSS/JS | 前端界面 | 无构建链，改完刷新即可，交作业时对方一行命令就能跑起来 | React/Vue（引入构建与依赖成本，对本项目无收益） |
| 自建轻量评测 | 检索质量回归 | 不引入 ragas 之类的重框架，指标透明、可解释 | 纯人工抽查（不可复现、无法对比改动前后） |

## 5. 运行效果

### 5.1 端到端实测（2026-09-24，接真实模型）

- 语料：2 篇资料（FastAPI 官方文档抓取的 26 个切片 + 课程讲义 2 个切片），共 28 个切片，全部为 1024 维真实向量（非哈希占位）
- 「FastAPI 是构建在哪两个库之上的？」→ `decision=generate`，Top1 相似度 0.612，6 条引用，端到端 5.2 秒，回答正确指出 Starlette 与 Pydantic
- 「切片长度和重叠范围会怎样影响召回质量？」→ 端到端 7.1 秒，回答分点说明「切太短会丢上下文、切太长会引入无关信息」
- 无关问题（贝尔不等式推导、深圳天气、红黑树实现、红楼梦结局、红烧肉做法）：全部走 `refuse` 分支，不调用生成模型

### 5.2 拒答阈值标定：一个真实踩到的坑

阈值一开始沿用 0.12，结果是 5 条无关问题**全部**进入了生成节点。虽然大模型最后还是回答了「上下文没有提供相关信息」，用户看到的结果没问题，但工作流轨迹里显示的是 `generate` 而不是 `refuse`——判断节点形同虚设。把分数打出来才看清楚边界：

| 问题类型 | Top1 相似度区间 |
| --- | --- |
| 相关问题（9 条） | 0.527 ~ 0.747 |
| 无关问题（5 条） | 0.224 ~ 0.413 |

两类之间存在一条干净的分界带，于是把 `MIN_RETRIEVAL_SCORE` 定在 0.45。改完复验：9 条相关问题仍然全部正常生成，5 条无关问题全部改走 `refuse`。

这个阈值和打分方式绑定：本地向量库的分数是 `0.8 × 余弦相似度 + 0.2 × 关键词覆盖率`，而 Qdrant 走纯余弦，量纲不同，换向量库或换 embedding 模型都需要重新标定。哈希兜底模式仍自动使用 0.05。

### 5.3 批量检索评测结果

评测集分两个套件，共 27 条用例（22 条可回答 + 5 条应拒答），固定写在 `scripts/evaluation_cases.json`。每条可回答用例都标注了「标准答案切片」，Recall / Precision / NDCG 都是拿它当标准算的。

**套件一：AI 应用开发**（2 篇文档、28 个切片，9 条可答 + 2 条应拒答）

| 配置 | Recall@k | Precision@k | NDCG@k | MRR | Hit Rate | 判定准确率 | 平均检索延迟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| top_k = 3 | 66.7% | 25.9% | 0.722 | 0.704 | 77.8% | 100% | 2.74 s |
| top_k = 5 | 83.3% | 20.0% | 0.818 | 0.759 | 100% | 100% | 668 ms |
| top_k = 10 | 83.3% | 10.0% | 0.818 | 0.759 | 100% | 100% | 2.56 s |

**套件二：机器学习**（5 篇课件 PDF、215 个切片，13 条可答 + 3 条应拒答）

| 配置 | Recall@k | Precision@k | NDCG@k | MRR | Hit Rate | 判定准确率 | 平均检索延迟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| top_k = 3 | 88.5% | 38.5% | 0.878 | 0.872 | 92.3% | 100% | 797 ms |
| top_k = 5 | 96.2% | 26.2% | 0.915 | 0.891 | 100% | 100% | 2.03 s |
| top_k = 10 | 100% | 13.8% | 0.917 | 0.891 | 100% | 100% | 708 ms |

复现命令：

```powershell
python scripts\run_evaluation.py                       # 两个套件，top_k 3 和 5
python scripts\run_evaluation.py --top-k 3 5 10 --refusal
python scripts\run_evaluation.py --suite 机器学习 --top-k 5
```

### 5.4 评测发现的问题（以及下一步怎么修）

**问题 1：AI 套件的 Recall 在 top_k=5 之后完全不再提升（83.3% → 83.3%）。**
漏掉的标准答案切片根本没进前 10 名，说明瓶颈不在「召回条数」，而在**语义匹配本身**：FastAPI 那篇是英文网页抓取的正文，切片里混着导航文字、代码片段和重复段落，中文提问去匹配这些切片天然吃亏。这类问题加 rerank（cross-encoder 精排）和查询改写（中文问题扩展成英文关键词/同义表述）是最直接的解法。

**问题 2：排序质量两头分化。** 机器学习的 NDCG 0.915，AI 应用开发只有 0.818，差在「对的切片能不能排进前两位」。同一个模型、同一套参数，换了语料就差这么多，说明排序质量跟材料形态强相关——中文课件切得干净，英文网页切片噪声大。

**问题 3：延迟长尾吓人。** 三次运行里各出现一次约 22 秒的检索请求（正常在 0.7 秒左右），平均延迟被硬拉到 2.5 秒。病因是远程 embedding 接口偶发抖动，而代码里只有 120 秒总超时、没有重试也没有缓存。要做的是：给 embedding 请求加超时+重试、对重复问题做向量缓存，或者把 embedding 换成本地模型（bge-m3 + Ollama）。

**问题 4：标注本身也会骗人。** 第一轮跑出来「FastAPI 是构建在哪两个库之上的？」Recall 是 0，查下来是我最初只标了 1 个切片，而这份材料里有两处都明确写了这个结论。校准脚本因此加了一条检查：把所有「同样包含全部期望词」但没被标注的切片列出来，提示人工复核。这条经验也说明，**评测体系本身的正确性需要单独验证**，否则你会拿着错的尺子调模型。

**已经确认站得住的部分：** 判定准确率在两个套件、27 条用例上都是 100%。无关问题的 Top1 分数最高只有 0.390，相关问题的 Top1 最低是 0.527，0.45 这条阈值在语料从 28 个切片扩到 243 个切片之后依然有效。

## 6. 评测体系是怎么建立的

**为什么用「问题 + 期望命中词 + 标准答案切片」这种两层结构。** 检索评测要回答两个问题：「该找的资料有没有被找回来」（召回）和「排得够不够靠前」（排序）。第一层用期望命中词做便宜的一致性检查，第二层用人工标注的标准答案切片算 Recall / Precision / NDCG——比纯人工打分便宜得多，也比纯关键词匹配严谨得多，而且能跟着代码一起版本化。

**测试集的构造原则。**

- 题目全部从已入库的切片反推，标注的标准答案切片必须真实存在（脚本会查 `/api/documents/{id}/chunks` 校验，防止写出不存在的切片）
- 期望词必须真的出现在标注切片里
- 脚本还会反过来查：哪些切片「同样包含全部期望词但没被标注」，列出来提示人工复核——5.4 里的问题 4 就是这么发现的
- 覆盖类型：术语型、跨切片综合型、中英文混合型，以及「资料里确实没有答案」的应拒答型
- 数据集固定不变，每次改动前后跑同一套，看指标涨跌

**指标定义（检索侧）。**

- Recall@k = 召回的相关切片数 / 标准答案切片总数。衡量「该找的有没有找全」，对多切片答案特别敏感。
- Precision@k = 召回的相关切片数 / 实际返回条数。k 越大越容易被稀释，所以它和 Recall 要一起看。
- NDCG@k = 带位置折扣的排序质量，相关内容排得越靠前分越高。衡量「排序好不好」。
- MRR = 平均 `1 / 首个相关切片排名`。第 1 位命中得 1 分，第 3 位只有 0.33 分。
- Hit Rate = top_k 里至少命中一条相关切片的用例比例。最宽松的指标。
- 关键词覆盖率 = 期望词在最佳命中切片里的占比。自研补充指标，衡量答案要素齐不齐。
- 平均检索延迟 = 「问题向量化 + 向量检索」的耗时，不含大模型生成，用来单独观察检索侧性能。

**指标定义（系统侧）。**

- 判定准确率 = （可回答的问题走了 `generate` + 应拒答的问题走了 `refuse`） / 总用例数。拒答阈值本身的标定过程见 5.2。

**和业界标准评测框架的对应关系。** 通用 RAG 评测框架（RAGAS、TruLens 这类）通常分四个维度：检索质量、上下文相关性、生成忠实度、答案相关性。本项目的覆盖情况：

| 评测维度 | 业界常见指标 | 本项目 |
| --- | --- | --- |
| 检索质量 | Recall@k、Precision@k、NDCG@k、MRR、Context Precision/Recall | ✅ 已实现，自带标注测试集 |
| 上下文相关性 | Context Relevance | ⚠️ 用 Top1 相似度分数近似 |
| 生成忠实度 | Faithfulness / Groundedness | ❌ 未实现，目前靠人工抽查，下一步上 LLM-as-judge |
| 答案相关性 / 正确性 | Answer Relevancy、Answer Correctness | ❌ 未实现，需要人工写参考答案 |
| 拒答与安全 | Abstention / Refusal Accuracy | ✅ 已实现（应拒答用例 + 判定准确率） |
| 系统性能 | 延迟、Token 成本 | ⚠️ 只测了检索延迟，成本未统计 |

**拒答怎么测。** 应拒答的用例直接写进测试集，和可回答用例一起跑，最后汇总成「判定准确率」；`scripts/run_evaluation.py --refusal` 还会额外走一遍完整的 `/api/chat` 链路，确认端到端也真的返回 `refuse`（而不是只有判断函数算对了）。

**阈值怎么定。** 不是拍脑袋定的，而是先跑一批相关问题与无关问题，把 Top1 分数打印出来找分界带（过程见 5.2）：相关问题最低 0.527，无关问题最高 0.413，取中间的 0.45。语料从 28 个切片扩到 243 个切片之后复验，无关问题最高分是 0.390、相关问题最低分是 0.527，阈值依然分得开。哈希兜底模式自动降到 0.05，避免切换 embedding 后端后所有问题都被拒绝。

**目前评测覆盖不到的地方。** 生成侧的三项（忠实度、答案相关性、答案正确性）还没量化，只做了人工抽查；Token 成本、端到端延迟的分布（P95/P99）也没统计——5.4 里那个 22 秒的长尾就是「只看平均值」会漏掉的问题类型。

## 7. 已知局限

- 测试集 27 条用例、覆盖 243 个切片，样本仍然偏小，指标只适合看趋势和做前后对比，不能当行业结论
- 标准答案切片是人工标注的。同一结论在课件里重复出现时，「重复页算不算相关」有主观空间（5.4 问题 4 就是标窄了导致的）；脚本会列出待复核项，但最终仍靠人判断
- 拒答阈值 0.45 是按当前语料和模型的分数分布标定的，换语料、换 embedding 模型或换向量库都需要重新标定
- 没有 rerank、没有查询改写——这是当前最大的效果短板，5.4 已定位到具体现象
- 延迟只统计了平均值，长尾没治：远程 embedding 接口偶发抖动能把单次检索拖到 20 秒以上
- `docker-compose.yml` 里的 PostgreSQL + Qdrant 配置已写好，但本机未安装 Docker，**没有实际运行验证**；当前真实运行的是 SQLite + 本地 JSON 向量存储
- 生成侧质量（忠实度、答案相关性）尚未量化，只有人工抽查
- 只支持单轮问答，多轮指代消解未实现

## 8. 后续可以做的方向

1. 接入 rerank 模型（如 `bge-reranker`）提升 MRR，把「召回 10 条再重排取 3 条」做成标准链路
2. 混合检索（向量 + BM25/关键词）改善专有名词、代码符号类问题的召回
3. LLM-as-judge 量化回答忠实度，补齐生成侧评测
4. 多轮对话与查询改写，处理「那它和 X 有什么区别」这类追问
5. 部署升级：原生 Qdrant 或 Docker Compose 的 PostgreSQL + Qdrant 方案

## 9. 常见追问速查

**Q：为什么 embedding 和生成模型要分开配置？**
A：两者职责不同，可以来自不同厂商。代码里 `EMBEDDING_*` 和 `LLM_*` 是两套独立配置，换其中任意一个都不影响另一个；`EMBEDDING_API_KEY` 留空时会自动复用 `LLM_API_KEY`，所以只有一个百炼 Key 时也能跑。

**Q：切片长度为什么是 700、重叠 100？**
A：按中文资料的篇幅经验值定的：700 字能容纳一个完整的知识点段落，100 字重叠保证跨切片的语义不被切断。这两个值在 `.env` 里，语料换成论文或代码文档时需要重新调。

**Q：为什么 Top1 分数低于阈值就直接拒绝？**
A：避免大模型在无依据的情况下编造，也避免把无关内容塞进上下文。阈值的来历是实测定标：相关问题 Top1 分数的最低值是 0.527，无关问题的最高值是 0.413，取中间值 0.45。阈值和打分方式绑定，换向量库或换 embedding 模型后要重新跑一遍标定，哈希模式则有独立的 0.05 低阈值。

**Q：为什么向量维度是 1024？**
A：`text-embedding-v3` 的默认输出维度就是 1024。维度必须和向量库集合一致，改动维度后需要重建索引，否则会报维度不匹配。

**Q：接入过程中踩过哪些坑？**
A：四个已经写进代码和文档的点：一是百炼兼容接口对 `text-embedding-v3` 的单次批量上限是 10，超出会返回 400，所以 `EMBEDDING_BATCH_SIZE=10`；二是换 embedding 后端必须重建索引，旧向量不能复用；三是 Key 失效会返回 401 `invalid_api_key`，检索和生成都会失败，需要在控制台重新生成；四是拒答阈值不能用默认的 0.12，否则无关问题照样进生成节点，必须按实际分数分布标定（见 5.2）。

**Q：没有 Docker 怎么部署？**
A：直接跑 `.\start.cmd` 就行，项目默认就是零依赖方案（SQLite + 本地向量文件）。Docker Compose 只是可选方案，用于需要 PostgreSQL 和 Qdrant 的场景。
